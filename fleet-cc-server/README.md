# Fleet Command & Control Server

Central web service for managing the Carputer fleet, tracking device status, orchestrating updates, and coordinating remote operations.

## Architecture

- **Frontend**: Next.js with TypeScript, SCSS modules, and GSAP animations
- **Backend**: Node.js API services with self-hosted Supabase (PostgreSQL + Auth + Realtime)
- **Deployment**: Docker Compose for container orchestration

## Features

- Device registration and heartbeat monitoring
- Version tracking and comparison
- Command dispatch and job queue
- Log and data synchronization
- Web-based dashboard with real-time updates
- Headquarters Wi-Fi auto-connect coordination

## Quick Start

### Initial Setup

```bash
# Run setup script (creates .env, installs dependencies, builds images)
./setup.sh

# Or manually:
# 1. Copy .env.example to .env and configure
# 2. Install dependencies: npm install (in backend/ and frontend/)
# 3. Build Docker images: docker-compose build
```

### Development

**Option 1: Run everything with Docker (recommended)**

```bash
# Start all services (Docker)
./dev.sh start
# or
make up

# Run database migrations
./dev.sh migrate
# or
make migrate

# Seed database with test devices (optional)
./dev.sh seed
# or
make seed

# Access services:
# - Dashboard: http://localhost:3000
# - API: http://localhost:3001
# - Supabase Studio: http://localhost:8080
```

**Option 2: Run services separately (requires PostgreSQL)**

```bash
# First, start PostgreSQL (via Docker or locally)
# If using Docker Compose, start just postgres:
docker-compose up -d postgres

# Then start backend/frontend individually:
./dev.sh backend   # Start backend only (needs PostgreSQL)
./dev.sh frontend  # Start frontend only (needs API running)
```

**Note:** When running backend/frontend outside Docker, you need:
- PostgreSQL running (either via Docker or installed locally)
- Database migrations run (`./dev.sh migrate` or `docker-compose exec api npm run db:migrate`)

### Other Commands

```bash
./dev.sh stop      # Stop all services
./dev.sh restart   # Restart all services
./dev.sh logs      # Show logs
./dev.sh status    # Show service status
./dev.sh clean     # Remove containers and volumes
```

## Environment Variables

The project uses separate `.env` files for backend and frontend:

### Backend Environment Variables

See `backend/.env.example` for required configuration. Copy to `backend/.env`:

```bash
cp backend/.env.example backend/.env
# Edit backend/.env with your configuration
```

Required variables:
- `DATABASE_URL` - PostgreSQL connection string (default: `postgres://postgres:postgres@localhost:5432/fleet_cc`)
- `SUPABASE_SERVICE_ROLE_KEY` - Supabase service role key (see below)
- `JWT_SECRET` - Secret for JWT tokens (generated by setup script)
- `SESSION_SECRET` - Secret for sessions (generated by setup script)
- `DEVICE_REGISTRATION_TOKEN` - Token for device registration (generated by setup script)

### Frontend Environment Variables

See `frontend/.env.example` for required configuration. Copy to `frontend/.env`:

```bash
cp frontend/.env.example frontend/.env
# Edit frontend/.env with your configuration
```

Required variables:
- `NEXT_PUBLIC_API_URL` - Backend API URL (default: `http://localhost:3001`)
- `NEXT_PUBLIC_SUPABASE_URL` - Supabase URL (default: `http://localhost:8000`)
- `NEXT_PUBLIC_SUPABASE_ANON_KEY` - Supabase anonymous key (see below)

### Supabase Keys (Self-Hosted)

For **self-hosted Supabase**, you need to generate the keys yourself. The `JWT_SECRET` is shared across all Supabase services (auth, realtime) and can be used as both the service role key and anon key.

**Quick setup:**
```bash
# Generate and set all Supabase keys automatically
./scripts/generate-supabase-keys.sh
```

**Manual setup:**
1. The `setup.sh` script generates `JWT_SECRET` automatically
2. Set `SUPABASE_SERVICE_ROLE_KEY` in `backend/.env` to the same value as `JWT_SECRET`
3. Set `NEXT_PUBLIC_SUPABASE_ANON_KEY` in `frontend/.env` to the same value as `JWT_SECRET`
4. Make sure `docker-compose.yml` uses the same `JWT_SECRET` for the `auth` and `realtime` services

**Why?** In self-hosted Supabase:
- `JWT_SECRET` is used by GoTrue (auth service) and Realtime to sign/verify tokens
- `SUPABASE_SERVICE_ROLE_KEY` = same as `JWT_SECRET` (gives full admin access)
- `SUPABASE_ANON_KEY` = same as `JWT_SECRET` (for client-side access)

The `setup.sh` script will automatically create these files from the examples and generate secure secrets.

## Test Data

The database can be seeded with test devices for development and testing:

```bash
./dev.sh seed
# or
make seed
```

**Test devices are clearly labeled:**
- Device IDs start with `TEST-` prefix (e.g., `TEST-001-ONLINE`)
- Hostnames start with `TEST-` prefix (e.g., `TEST-carputer-alpha`)
- VINs start with `TEST-VIN-` prefix

**To remove all test devices:**
```sql
DELETE FROM devices WHERE device_id LIKE 'TEST-%';
```

The seed script creates a variety of test devices with different statuses (online, offline, stale) to test sorting and filtering functionality.
